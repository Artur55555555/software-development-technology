# 1. Что такое разработка ПО

**Разработка программного обеспечения** — это процесс создания, тестирования, внедрения и сопровождения программ.

Обычно разработка включает несколько этапов:

```text
Идея
  ↓
Анализ требований
  ↓
Проектирование
  ↓
Написание кода
  ↓
Тестирование
  ↓
Релиз
  ↓
Поддержка и улучшение
```

Главная задача разработчика — не просто написать код, который работает, а создать систему, которую будет удобно:

* понимать;
* изменять;
* тестировать;
* расширять;
* исправлять;
* поддерживать.

# 2. Основные принципы разработки

Существует множество принципов программирования. Некоторые из самых известных:

| Принцип                        | Основная идея                                                  |
| ------------------------------ | -------------------------------------------------------------- |
| **KISS**                       | Делай решение максимально простым                              |
| **DRY**                        | Не повторяй один и тот же код                                  |
| **YAGNI**                      | Не реализуй то, что сейчас не требуется                        |
| **SRP**                        | Один компонент — одна ответственность                          |
| **OCP**                        | Код должен быть открыт для расширения, но закрыт для изменения |
| **Разделение ответственности** | Разные части системы должны выполнять разные задачи            |
| **Композиция**                 | Сложное поведение лучше собирать из небольших компонентов      |

---

## 2.1 KISS

**KISS — Keep It Simple, Stupid.**

Смысл принципа: **если задачу можно решить простым способом, не нужно усложнять решение.**

### Плохо

```python
def is_adult(age):
    if age >= 18:
        return True
    else:
        return False
```

### Лучше

```python
def is_adult(age):
    return age >= 18
```

Второй вариант короче и сразу показывает смысл функции.

### Главное

> Простое решение обычно легче понять, протестировать и изменить.

---

## 2.2 DRY

**DRY — Don't Repeat Yourself.**

Не следует многократно копировать одинаковую логику.

### Плохо

```python
price1 = price1 * 0.9
price2 = price2 * 0.9
price3 = price3 * 0.9
```

### Лучше

```python
def apply_discount(price):
    return price * 0.9

price1 = apply_discount(price1)
price2 = apply_discount(price2)
price3 = apply_discount(price3)
```

Теперь если размер скидки изменится, достаточно изменить одну функцию.

### Однако

DRY не означает, что **любое повторение строк кода нужно немедленно выносить в функцию**.

Иногда небольшое дублирование делает код понятнее, чем слишком сложная абстракция.

---

## 2.3 YAGNI

**YAGNI — You Aren't Gonna Need It.**

Не нужно реализовывать функциональность заранее, если она пока не нужна.

### Например

Допустим, сейчас приложение поддерживает только пользователей из одной страны.

Не стоит заранее создавать сложную систему для:

* 50 стран;
* 20 валют;
* 15 языков;
* нескольких налоговых систем,

если требований на это пока нет.

### Идея

```text
Требуется сейчас → реализуем

Возможно понадобится когда-нибудь → пока не реализуем
```

Это позволяет уменьшить количество лишнего кода.

---

## 2.4 Разделение ответственности

Каждая часть программы должна заниматься своей задачей.

Например, приложение интернет-магазина может иметь:

```text
UserService
    ↓
Работа с пользователями

OrderService
    ↓
Работа с заказами

PaymentService
    ↓
Работа с платежами

EmailService
    ↓
Отправка писем
```

Не стоит помещать всю бизнес-логику приложения в один огромный класс или файл.

---

## 2.5 Принцип единственной ответственности (SRP)

**SRP — Single Responsibility Principle.**

Класс или функция должны иметь **одну основную ответственность**.

### Плохой пример

```python
class User:
    def save_to_database(self):
        pass

    def send_email(self):
        pass

    def generate_report(self):
        pass
```

Класс `User` занимается сразу несколькими задачами.

### Более подходящий вариант

```python
class User:
    pass


class UserRepository:
    def save(self, user):
        pass


class EmailService:
    def send(self, user):
        pass


class ReportService:
    def generate(self, user):
        pass
```

Теперь ответственность разделена.

---

## 2.6 Принцип открытости/закрытости (OCP)

**OCP — Open/Closed Principle.**

Программные компоненты должны быть:

* **открыты для расширения**;
* **закрыты для изменения существующей логики**.

Например, вместо большого `if`:

```python
if payment_type == "card":
    ...
elif payment_type == "paypal":
    ...
elif payment_type == "crypto":
    ...
```

можно использовать отдельные реализации:

```python
class CardPayment:
    def pay(self, amount):
        pass


class PayPalPayment:
    def pay(self, amount):
        pass


class CryptoPayment:
    def pay(self, amount):
        pass
```

Тогда добавление нового способа оплаты не требует переписывать существующие классы.

---

## 2.7 Композиция вместо наследования

Иногда вместо создания сложной иерархии классов лучше объединять небольшие компоненты.

Например:

```text
Car
 ├── Engine
 ├── GPS
 └── AudioSystem
```

Автомобиль **содержит** двигатель, GPS и аудиосистему.

Такой подход называется **композицией**.

Он позволяет заменять отдельные компоненты независимо друг от друга.

# 3. Чистый код

**Clean Code** — код, который легко читать, понимать и изменять.

### Основные правила

* Использовать понятные названия.
* Делать функции небольшими.
* Не создавать огромные классы.
* Избегать ненужных комментариев.
* Не дублировать код.
* Соблюдать единый стиль.

### Плохое название

```python
x = 15
```

### Хорошее название

```python
user_age = 15
```

Название переменной должно объяснять её назначение.

---

## Пример

### Плохо

```python
def calc(a, b, c):
    x = a * b
    y = x - c
    return y
```

### Лучше

```python
def calculate_final_price(price, quantity, discount):
    total_price = price * quantity
    final_price = total_price - discount

    return final_price
```

Второй вариант длиннее, но его значительно легче понять.

# 4. Структура проекта

Хорошая структура проекта помогает быстро находить нужный код.

Например:

```text
project/
│
├── src/
│   ├── models/
│   ├── services/
│   ├── controllers/
│   └── utils/
│
├── tests/
│   ├── unit/
│   └── integration/
│
├── docs/
│
├── README.md
├── .gitignore
└── requirements.txt
```

### Возможное назначение каталогов

| Каталог        | Назначение              |
| -------------- | ----------------------- |
| `src/`         | Основной исходный код   |
| `models/`      | Модели данных           |
| `services/`    | Бизнес-логика           |
| `controllers/` | Обработка запросов      |
| `utils/`       | Вспомогательные функции |
| `tests/`       | Тесты                   |
| `docs/`        | Документация            |

Структура зависит от языка и типа проекта, поэтому не существует единственной правильной структуры для всех приложений.

# 5. Работа с Git

**Git** — система контроля версий.

Она позволяет:

* сохранять историю изменений;
* создавать ветки;
* работать нескольким разработчикам;
* возвращаться к предыдущим версиям;
* просматривать изменения.

### Основной workflow

```text
Изменение файлов
      ↓
git add
      ↓
git commit
      ↓
git push
      ↓
GitHub
```

### Пример

```bash
git add .
git commit -m "Add user authentication"
git push
```

### Хороший commit

```text
Add user authentication
```

### Плохой commit

```text
fix
```

или

```text
changes
```

Сообщение commit должно объяснять, что именно было изменено.

# 6. Тестирование

Тестирование помогает находить ошибки до того, как они попадут к пользователям.

Основные виды тестов:

| Тип                | Что проверяет                             |
| ------------------ | ----------------------------------------- |
| Unit-тест          | Отдельную функцию или небольшой компонент |
| Integration-тест   | Взаимодействие нескольких компонентов     |
| E2E-тест           | Работу системы целиком                    |
| Регрессионный тест | Что старый функционал не сломался         |

### Пример unit-теста

Допустим, есть функция:

```python
def add(a, b):
    return a + b
```

Тест:

```python
def test_add():
    assert add(2, 3) == 5
```

Тестирование особенно важно для критически важной бизнес-логики.

# 7. Документирование

Даже хороший код может быть сложным для нового разработчика.

Поэтому проект должен иметь документацию.

Минимальный набор:

```text
README.md
│
├── Описание проекта
├── Установка
├── Запуск
├── Использование
├── Требования
└── Контакты / ссылки
```

### Пример README

````markdown
# My Project

## Описание

Простое веб-приложение для управления задачами.

## Установка

```bash
git clone https://github.com/example/project.git
cd project
pip install -r requirements.txt
````

## Запуск

```bash
python main.py
```

````

Хорошая документация экономит время разработчикам.

# 8. Обработка ошибок

Ошибки должны обрабатываться предсказуемо.

### Плохо

```python
try:
    result = calculate()
except:
    pass
````

Проблема: ошибка полностью скрывается.

### Лучше

```python
try:
    result = calculate()
except ValueError as error:
    print(f"Некорректное значение: {error}")
```

Важно:

* не скрывать ошибки без причины;
* использовать подходящий тип исключения;
* давать понятные сообщения;
* логировать важные ошибки;
* не показывать пользователю конфиденциальные данные.

# 9. Безопасность

Безопасность должна учитываться ещё во время разработки.

Основные правила:

* не хранить пароли в исходном коде;
* не хранить API-ключи в Git;
* проверять входные данные;
* использовать безопасные методы авторизации;
* обновлять зависимости;
* ограничивать права пользователей;
* не доверять данным от клиента.

### Плохо

```python
DATABASE_PASSWORD = "my-secret-password"
```

### Лучше

Использовать переменные окружения:

```python
import os

DATABASE_PASSWORD = os.getenv("DATABASE_PASSWORD")
```

И добавить секретные файлы в `.gitignore`.

# 10. Пример хорошего подхода

Представим задачу:

> Нужно создать функцию регистрации пользователя.

Не стоит сразу писать всё в одном месте.

### Плохой вариант

```python
def register_user(name, email, password):
    # проверка данных
    # хеширование пароля
    # работа с БД
    # отправка email
    # создание ответа
    ...
```

Функция выполняет слишком много задач.

### Более структурированный вариант

```text
RegistrationService
        │
        ├── Validator
        │
        ├── PasswordHasher
        │
        ├── UserRepository
        │
        └── EmailService
```

Каждый компонент отвечает за свою задачу.

### Преимущества

| Подход                 | Результат              |
| ---------------------- | ---------------------- |
| Большая функция        | Сложно тестировать     |
| Много обязанностей     | Сложно изменять        |
| Разделение компонентов | Проще тестировать      |
| Понятные названия      | Проще читать           |
| Небольшие функции      | Проще переиспользовать |

# 11. Чек-лист разработчика

Перед отправкой кода можно проверить:

### Код

* [ ] Названия переменных понятны.
* [ ] Функции не выполняют слишком много задач.
* [ ] Нет ненужного дублирования.
* [ ] Нет лишнего усложнения.
* [ ] Код соответствует стилю проекта.

### Тесты

* [ ] Основная логика покрыта тестами.
* [ ] Проверены обычные случаи.
* [ ] Проверены ошибочные случаи.

### Git

* [ ] Commit имеет понятное название.
* [ ] В репозиторий не попали секреты.
* [ ] В commit нет лишних файлов.

### Документация

* [ ] Обновлён README при необходимости.
* [ ] Сложная логика имеет объяснение.
* [ ] Инструкции по запуску актуальны.

### Безопасность

* [ ] Пароли не находятся в коде.
* [ ] API-ключи не находятся в Git.
* [ ] Входные данные проверяются.
* [ ] Ошибки не раскрывают секретную информацию.

# 12. Заключение

Основные принципы разработки ПО помогают создавать программы, которые не только работают сегодня, но и остаются удобными для развития в будущем.

Самые важные идеи:

> **KISS** — не усложняй без необходимости.

> **DRY** — избегай ненужного дублирования.

> **YAGNI** — не реализуй функциональность заранее.

> **SRP** — разделяй ответственность.

> **Clean Code** — пиши код, который легко читать.

> **Тестирование** — проверяй работу программы автоматически.

> **Git** — сохраняй историю изменений.

> **Документация** — объясняй, как работает проект.

> **Безопасность** — учитывай её на всех этапах разработки.
